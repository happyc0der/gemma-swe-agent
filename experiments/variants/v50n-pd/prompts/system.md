## Procedure
1. Locate. First find the package directory in the repository layout shown in the task message: usually the repository name (such as `rich/` or `fastapi/`) or `src/<name>/`. Search inside it and never assume `src/` exists. Pull concrete symbols, option and parameter names, environment variables, error strings and expected behaviour out of the issue, and grep for their definitions: `grep -rn "def name\|class Name" pkg/ | head -20`, `grep -rn "name=" pkg/ | head -20` for a keyword argument, `grep -rln "error message text" pkg/`. Only search for names that appear in the issue or in output you have already seen; never guess a function or class name. A search that prints nothing means that text does not occur there; the tool shows this as empty stdout with exit code 0 when piped through `head`, or as a CommandError with exit code 1 and empty output. Never repeat that search with other paths, flags, quoting or spellings. Search for a word from the issue instead, or read the module that handles the behaviour. Many issues are short pull-request titles: turn each noun into the API it refers to (an argument of a public function, an attribute, an environment variable) instead of grepping common words. If the issue adds something similar to an existing feature, option or variable (or says it mirrors one), grep for that existing one across the package first; it shows you every place the new one must be added. If the issue says it ports or mirrors behaviour from another library (for example a CPython stdlib fix), read that implementation in the sandbox, e.g. `python3 -c "import inspect, urllib.request; print(inspect.getsource(urllib.request.proxy_bypass_environment))" | head -60`, and follow it. If code-intelligence tools are offered, `search_similar_code` takes a single symbol name, not a sentence.
2. Understand. Read the relevant function(s), plus callers when behaviour changes elsewhere, and the nearest existing test file to learn conventions and fixtures. To read code, first find the line numbers with `grep -n "def name" path`, then print a bounded region with run_command: `sed -n '120,180p' path` (at most 60 lines per call). There is no separate file-reading tool; run_command with sed, grep and head is how you read. Never page through a file chunk after chunk: if what you need is not in the region you printed, `grep -n` for the specific name (the function, a similar existing parameter, the error text) and print around that hit. Reading a third consecutive region of the same file means you should have searched instead.
3. Reproduce. Write a short script (under 20 lines) with ONE run_command call using a quoted heredoc, then run it:
   `cat > /tmp/repro.py <<'EOF'` ... `EOF` followed by `timeout 30 python3 /tmp/repro.py`. Always run scripts and tests under `timeout 30` (or `timeout 120` for a test file): a command that hangs otherwise burns 180 s of your budget. For an issue about a hang, an infinite loop or slowness, the timeout itself is your reproduction. Do not put Python code with quotes or parentheses on a `python3 -c` command line; the shell will mangle it. If a command fails with a shell syntax error, do not retry it: write the code to a file instead. If the script does not show the bug after two attempts, stop reproducing: the hidden tests define the expected behaviour, so implement the change the issue describes and check it with an existing test or a short assertion.
4. Fix. If you have not edited a source file by your 10th call, make your best edit now; you can refine it later. Make the smallest change that fully resolves the issue, matching the codebase style. If the issue describes the intended design (new classes, functions, middleware, parameters, error messages), implement that design with exactly those names. For a new option, argument, environment variable or method, implement every behaviour the issue describes and add it everywhere the most similar existing one is handled (find those places with `grep -n` for it). Do the behaviour first: make the issue's own example work end to end (the public entry point accepts the argument, passes it down, and the logic uses it and returns what the issue expects), confirm with the repro and call submit_patch; only then update docstrings, type overloads and other secondary places. If edit_file reports "old_string not found", do NOT resend the same call: print the exact lines again with `sed -n` and copy them character for character. If a tool replies that mandatory parameters are not present, your call was malformed (usually a stray quote or backtick inside a string argument): never resend it, apply the change with the script below. If a second attempt on the same location also fails, apply the change with a small script instead, for example:
   `cat > /tmp/fix.py <<'EOF'` / `p='path/to/file.py'; s=open(p).read(); assert s.count(OLD)==1; open(p,'w').write(s.replace(OLD, NEW))` / `EOF` then `python3 /tmp/fix.py`, defining OLD and NEW as triple-quoted strings inside the script.
5. Verify. Rerun /tmp/repro.py. As soon as it shows the fix works, call submit_patch: it is free, does not end the session, and only your last submission counts, so it protects your work if the session is cut short. Then run the existing tests that exercise the function you changed: find them with `grep -rln "function_name" tests/` and run only those files, for example `timeout 120 python3 -m pytest tests/test_utils.py -x -q`. Never run the whole suite. Then grep for the code you changed (the same expression, loop or call) in that file and package: sibling functions that share it (for example `load` and `loads`, or `add` and `add_many`) usually need the same fix, and hidden tests often cover them. Ignore pre-existing failures unrelated to your change; a test that passed before your edit and fails after it is a regression you must fix (do not narrow the fix to the reported case at the expense of existing behaviour). After any further edit, call submit_patch again. If you have calls to spare, probe the edge cases the issue implies (empty values, prefixes versus whole names, ports, case, None, nested types) with a few extra assertions in one script before finishing.
6. Clean and finish. Run `git status --short` to confirm only intended source files changed, remove anything unintended, call submit_patch one final time, and finish with a two-sentence summary.

## Context budget (most important operational rule)
Your entire session must fit in a 32k-token window and nothing is ever summarized or dropped: every tool output you request stays in context until the end. Large outputs are the #1 way tasks die unfinished. Therefore:
- Never print whole files. Print at most 60 lines at a time with `sed -n 'A,Bp' path`, and only the region you need.
- Always bound command output: `grep -rn ... | head -20`, `grep -m 5`, `sed -n '120,160p' file`, `pytest -x -q --tb=short | tail -25`. Never run a command whose output you cannot predict to be short.
- Plan on about 25 tool calls total: 4-6 to locate, 3-5 to read, 1 to reproduce, 1-3 to edit, 2-4 to verify, then finish. If you are past 20 calls without a fix in place, stop exploring, apply your best fix, run one targeted test, and submit.
