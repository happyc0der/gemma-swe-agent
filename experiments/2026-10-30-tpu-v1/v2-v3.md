# TPU v2 (10-31) and v3

v2 (commit 5e77930; machine report, weights on a real disk, RAM guard on /proc/meminfo) queued ~28 h (pushed 10-30
01:50 UTC, RUNNING by ~05:50 UTC 10-31) and ended in ERROR at ~07:10 UTC after 1.30 TPU h, again with no files at all
and an empty log (`kaggle kernels output` and the API's ListKernelSessionOutput both return nothing). v1 died after
1.25 TPU h, so both runs die at ~75-78 min and the session's /kaggle/working is lost with them.

Not yet known whether the cause is memory, disk, the download, vLLM's load/compile, or a session limit. Two changes in v3:
- The guard now reads the container's cgroup (limit, anon + shmem, all charged memory); /proc/meminfo shows the host,
  but the container is killed at its own limit. res.log every 15 s, with weights-dir and /kaggle/working sizes every minute.
- `diag_exit_min` = 45: the run reports (du, df, free, top processes by RSS), kills its whole process tree and exits
  cleanly at 45 min, well before the ~75 min mark, so Kaggle should save run.log, res.log and result.json. That shows
  how far it gets in 45 min and what memory looked like; the next version fixes the actual cause.

Smoke test (docker python:3.12-slim, --memory 6g, data/tpu_smoke/v3): cgroup limit read as 6 GB; with diag_exit_min 0.5
and a 120 s child in place of the vllm-tpu install, it exited after 30 s with rc 0, verdict "diag exit after 0.5 min",
all three files written, and no child left running. The TPU itself can only be tested on Kaggle.

## v3 result (11-01) and v4

v3 queued ~31 h (pushed 10-31 07:25 UTC), ran 15:06-15:53 UTC 11-01 and exited at 45 min as designed; **its files came
back** (data/tpu_results/v3: run.log, res.log, result.json, kernel log). 1.31 TPU h.

- Machine: TPU v5litepod-8 (8 chips seen by jax 0.11.2), 377 GB host RAM, cgroup limit 330 GB, overlay root with
  1.09 TB free, /kaggle/working a 21 GB ext4 loop device. Neither RAM nor disk space was ever short.
- Timeline: uv + vllm-tpu 0.32.0 venv 4 min; `import vllm, jax` OK; download started 15:11:32.
- The disk is the problem. ~47 GB of weights landed in the page cache within a minute (cgroup "charged" 20 -> 94 GB),
  then the weights dir grew at ~25 MB/s (46.7 GB at 15:12:35 -> 59.7 GB at 15:21) as writeback throttled the writer.
  All 59,680 MiB (= the full 62.6 GB) were there by 15:21, yet snapshot_download never returned (15:21-15:51), and at
  the exit even `du -sm /tmp/gemma-work/*` hung > 120 s. A ~60 GB dirty backlog on a ~25 MB/s disk stalls all I/O
  for ~40 min; v1 and v2 then went on to load the weights and died at ~75 min with nothing saved, consistent with
  Kaggle's own output saving stalling too (its /kaggle/working is a loop device on the same host disk).

v4: weights in RAM (/dev/shm if >= 75 GB free, else a tmpfs mount if allowed); failing both, on disk one file at a time
with os.sync() after each so the backlog never exceeds one shard. res.log adds host Dirty/Writeback. diag_exit_min = 120
now only fires if vLLM is not serving by then, so a working run continues to the checks, benchmark and stage 2
(canary, then pub-budget-fit and bf-nomatch on AB with thinking on). Smoke test (docker, tiny repo, lowered size
thresholds; data/tpu_smoke/v4): weights -> /dev/shm, per-file log, dirty/writeback columns, vLLM pointed at the RAM dir.
